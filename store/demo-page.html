用状态机重写播放器控制层

2026-10-12 · 14 分钟阅读

播放器控制层是最容易写成面条代码的地方：暂停、缓冲、拖动进度、切集、投屏、倍速、 字幕切换，这些状态彼此耦合，任何一个操作都可能触发其它状态的连锁反应。 这篇文章记录我们如何用显式状态机把这些行为重新组织，让每个分支都能被单独推理和测试。

为什么需要状态机

传统的布尔标记写法会很快失控：isPlaying、isBuffering、isSeeking、isEnded 四个标记 理论上能组合出十六种状态，而其中只有五种是合法的。当非法状态出现时， 界面上就会同时出现加载动画和播放按钮，用户点击后行为完全无法预测。

状态机的价值在于把「合法状态的集合」写成代码本身。一旦状态被限制在五个节点之内， 我们就能枚举所有迁移路径，把每一个迁移都作为一条测试用例固定下来， 而不是依赖某位同事对旧代码的记忆。

从布尔标记到显式状态

第一步是把布尔标记替换成一个字符串状态：idle、loading、playing、paused、error。 这一步本身不会改变行为，但它让所有分支第一次变得可见， 我们也就是在这次重写里发现了三个从未被覆盖的死分支。

设计状态与事件

状态机由三部分组成：状态集合、事件集合、迁移函数。状态代表某一时刻播放器的完整描述， 事件代表来自外部世界的输入——用户操作、网络回调、定时器触发都算事件。 迁移函数是纯函数：给定当前状态与事件，返回下一个状态与需要执行的副作用。 

type State = 'idle' | 'loading' | 'playing' | 'paused' | 'error';
type Event =
  | { type: 'PLAY_REQUESTED' }
  | { type: 'MEDIA_READY' }
  | { type: 'MEDIA_ENDED' }
  | { type: 'ERROR'; message: string };

function reduce(state: State, event: Event): { next: State; effects: Effect[] } {
  switch (state) {
    case 'idle':
      if (event.type === 'PLAY_REQUESTED') return { next: 'loading', effects: [load()] };
      break;
    case 'loading':
      if (event.type === 'MEDIA_READY') return { next: 'playing', effects: [play()] };
      if (event.type === 'ERROR') return { next: 'error', effects: [report(event.message)] };
      break;
    // …
  }
  return { next: state, effects: [] };
}

把副作用写成返回值而不是直接调用，是这套设计里最关键的一步： 状态机本身变成可测试的纯逻辑，真正碰 DOM 与网络的代码被压缩到很薄的执行器里。

错误也要是状态

很多实现把错误当成异常往上抛，结果是每个调用点都要写一遍兜底逻辑。 把错误建模成一个状态之后，「重试」就只是 error 状态下的一条普通迁移， 界面的展示也统一由状态决定，不再需要在各处捕获异常。

迁移过程中的三个坑

重写播放器控制层并不是一次可以悄悄完成的重构，它牵涉到埋点、A/B 实验与线上灰度。 我们在两周内分三步切换，这里记录其中三个真正让人头疼的问题。

事件乱序

网络回调与用户操作会以任意顺序到达：用户在 loading 阶段就要暂停， 而 MEDIA_READY 可能在这之后才回来。状态机对此的处理很直接—— 在 loading 状态下收到 PAUSE_REQUESTED 时记录一个「期望暂停」的标记， 等 MEDIA_READY 到达后直接进入 paused，而不是播放一秒再暂停。

把「用户的意图」和「系统的状态」分开记录，是解决乱序问题的通用手段。

投屏与本地播放的差异

投屏之后，播放进度不再由本地时钟决定，进度回调的频率也从每秒一次降到几秒一次。 我们给状态机补了一条 remote 维度，把本地与远端的差异限制在效果执行器里， 状态与迁移逻辑保持不变。

结果与数值

重写完成后，播放相关的线上报错下降了 74%，与播放状态相关的客服反馈从每周十余条降到个位数； 更直观的收益是新增功能的速度：接入倍速与字幕切换只用了两天， 而在旧实现里，类似的改动通常需要一周以上。

测试覆盖

我们为每条迁移写了单元测试，用一个简单的表格驱动：给定状态与事件， 断言下一个状态与需要执行的副作用。这份表同时也是文档， 新人接手时先读它，再读代码。
